# PicoPics 全栈部署到 az-japan（Azure VM）方案

## 目标架构（单域名，无 CORS）

```
用户浏览器 ── https://<域名> ──> Caddy (:80/:443, 自动HTTPS)
  ├─ POST /auth/callback、/upload、/api/*(除/api/history) ──> Node 网关 :8080
  │    ├─ uploader.ts（Hono，原样复用）← GitHub OAuth/上传/删除/配额/管理
  │    └─ CF 兼容层：R2→本地磁盘、D1→SQLite、Durable Objects→进程内实例+SQLite持久化、caches.default→内存Map
  ├─ GET /api/history ──> 同一网关内的 history.ts（原样复用）
  ├─ GET /images/* ──> 同一网关内的 cdn.ts（原样复用）
  └─ 其余所有路径（含 GET /auth/callback 页面）──> Next.js standalone :3000
```

- **核心思路**：三个 worker 都是标准 Hono 应用，Cloudflare 依赖只集中在 env 绑定接口（R2 put/get/delete/head、D1 prepare/bind/first/run/all、DO idFromName/get/fetch、caches.default、CF-Connecting-IP）。写一个 Node 兼容层实现这些接口，**worker 代码一行不改**地跑在 VPS 上。DO 的业务逻辑（UploadQuota/IPBlacklist 类）也直接实例化复用，只 shim 它的 storage。
- 数据：SQLite `/var/lib/picopics/db.sqlite`（user_images/user_profiles/user_settings 三表，DDL 从现有查询反推，建表语句入库）；图片存 `/var/lib/picopics/images/`（按对象键路径落盘 + content-type 边车文件）。
- 内存预算（853Mi）：Next ~250M + 网关 ~150M + Caddy ~30M，先加 2G swap 兜底；**构建全部在本地 WSL 完成**，服务器只跑产物。

## 一、仓库改动（提交到 dev）

1. **`app/auth/callback/page.tsx:47`**：token 交换 URL 从硬编码 `https://api.hiaplha.xyz/auth/callback` 改为 `${process.env.NEXT_PUBLIC_UPLOAD_API || "https://api.hiaplha.xyz"}/auth/callback`（不传 env 时行为不变，不影响现有 CF 生产）。
2. **`next.config.js` env 块**：默认值改为 `process.env.X ?? "https://..."` 形式，使构建时显式传入的 `NEXT_PUBLIC_UPLOAD_API/HISTORY_API` 能覆盖 hiaplha.xyz 默认值。
3. **`workers/cdn.ts` 修复**：`app.get("/:key")` → `app.get("/:key{.+}")`——多段对象键（`images/日期/uuid.png`）现在根本匹配不到该路由，这是现存 bug，顺带修复（单段键行为不变）。
4. **新增 `server/` 目录**（Node 网关，不进入 Next 构建）：
   - `server/cf-compat/`：`r2.ts`（磁盘实现 put/get/delete/head，含路径逃逸防护）、`d1.ts`（better-sqlite3 实现 prepare/bind/first/run/all，结果形状对齐 D1）、`durable-objects.ts`（idFromName/get → 实例化 uploader.ts 导出的 DO 类，storage 用内存 Map + do_storage 表写透持久化）、`caches.ts`（TTL 遵循 Cache-Control 的内存缓存）、`cf-headers.ts`（把 Caddy 传来的 X-Forwarded-For 注入为 CF-Connecting-IP）。
   - `server/gateway.ts`：@hono/node-server 启动，按路径分发三个 worker app（uploader 默认 / /upload /auth/callback /api/*；/api/history → history；/images/* → cdn），加载 .env 组装 env 对象，启动时执行 schema.sql。
   - `server/schema.sql`、`server/package.json`（仅 @hono/node-server、hono、better-sqlite3、dotenv）。
   - `server/gateway.test.ts`：复用现有 uploader.test.ts 的 stub 手法，冒烟测试 health + 上传→落盘→D1 记录→删除 全链路。
5. **新增 `deploy/az-japan/`**：`Caddyfile`（方法匹配：POST /auth/callback → 8080；/upload、/api/*、/images/* → 8080；其余 → 3000）、`picopics-api.service`、`picopics-web.service`（systemd，EnvironmentFile=.env，Restart=always）、`.env.example`。
6. **新增 `scripts/deploy-vps.sh <域名>`**：本地构建（`NEXT_PUBLIC_UPLOAD_API=https://域名 npm run build`）→ esbuild 打包 gateway → rsync（standalone+static+public+server bundle）→ 远程 npm ci + systemctl restart。
7. **新增 `docs/vps-deploy.md`**：记录架构、运维命令、故障排查。

## 二、服务器准备（az-japan，SSH + sudo）

1. `fallocate 2G swap`（先兜底内存）；安装 Node 22 LTS（NodeSource）、Caddy（官方源）——VM 已有 docker 源但不用 Docker（内存不够）。
2. 创建 `/opt/picopics`（代码产物）、`/var/lib/picopics`（数据，属主 picopics 服务用户）。
3. 写入 systemd 单元 + Caddyfile（域名占位，拿到域名后填入并 reload）。

## 三、需要你提供/操作的（部署前）

1. **域名** + DNS A 记录 → VM 公网 IPv4。
2. **Azure**：VM 加公网 IP；NSG 入站放行 80/443（TCP，任意源）。
3. **GitHub OAuth App**（Developer settings → OAuth Apps，回调 URL 填 `https://<域名>/auth/callback`）→ 把 **Client ID / Client Secret** 发到对话里。
4. **Telegram**：@BotFather 建 bot → 把 **Bot Token** 和接收通知的 **Chat ID** 发到对话里。
5. ADMIN_TOKEN 由我随机生成写入服务器 .env。

## 四、部署与验证

1. 提交仓库改动 → 本地 `tsc`/`biome`/`vitest`（含新网关测试）全绿。
2. 跑 `scripts/deploy-vps.sh` → Caddy 签发证书。
3. 验证链：`/health` → GitHub OAuth 真实登录回环 → curl 上传一张图 → 确认磁盘落盘 + SQLite 记录 + `https://域名/images/...` 可访问 → 删除 → 配额接口生效 → admin 面板（stats/users/images）可用 → Telegram 收到通知。
4. 现有 hiaplha.xyz 的 Cloudflare 部署完全不动。

## 已知限制（如实记录，不隐瞒）

- cdn 的 `?w/h` 缩略图走 Cloudflare Image Resizing 重定向，VPS 上不可用（客户端未使用该参数，不影响）。
- worker 里 IP 黑名单管理路由与 DO 的已知缺陷（admin 写入 `global` 实例而检查用 per-IP 实例）原样保留——保持与 CF 行为一致，不在本次修复范围。
- 服务器单机无冗余；SQLite 每日无需备份脚本但会在 docs 里给出备份命令。
